# Free web deployment

Frontend on Cloudflare Pages, API on Render (free), Postgres on Neon (free). Nothing secret lives in the repo. Follow the steps in order: the API refuses to start in Production without a CORS origin, so the frontend URL has to exist before the API is deployed.

## 1. Database (Neon)
1. Sign up at neon.tech and create a project (region close to the Render region, e.g. Frankfurt).
2. Copy the connection details: host, database, user, password. Neon shows the pooled host (it contains `-pooler`) by default. Use the **direct** host (without `-pooler`) for the Liquibase migration, since DDL and Liquibase locks behave better without the pooler. The API connection string can use either.
3. In GitHub: Settings > Secrets and variables > Actions. Add secrets `NEON_JDBC_URL` (`jdbc:postgresql://<direct-host>/<db>?sslmode=require`), `NEON_DB_USER`, `NEON_DB_PASSWORD`, and the variable `DEPLOY_ENABLED=true`.
4. Run the "Migrate database" workflow once (Actions tab > Run workflow). It also runs on every push to main that touches `database/`. Overlapping runs are queued, not run in parallel.

## 2. Frontend project (Cloudflare Pages), first pass
1. dash.cloudflare.com > Workers & Pages > Create > Pages > connect the GitHub repo.
2. Root directory `frontend`, build command `npm run build`, output `dist`.
3. Pick the project name and note the URL `https://<project>.pages.dev` (or use a custom domain). The first build can fail or point at no API; that is fine, you redeploy in step 4.

## 3. API (Render)
1. Sign up at render.com with GitHub, then New > Blueprint and pick this repo (it reads `render.yaml`).
2. Fill the prompted env vars:
   - `ConnectionStrings__DefaultConnection`: `Host=<host>;Database=<db>;Username=<user>;Password=<password>;SSL Mode=Require`
   - `AiCoach__ApiKey`: your OpenRouter key
   - `Cors__AllowedOrigins__0`: the Pages URL from step 2 (no trailing slash). Only this exact origin is allowed, so preview deployments on other `*.pages.dev` URLs are blocked by CORS.
3. Note the API URL, e.g. `https://gymrat-api.onrender.com`.

`JwtSettings__Key` and `PasswordSettings__Pepper` are generated by Render. Rotating the JWT key logs everyone out. Rotating the pepper breaks every existing password, so never change it once users exist.

`render.yaml` pins `PORT=8080`, which is the port the image listens on.

### Rate limits behind Render's proxy
Login and registration limits are per client address. Render's proxy sits in front of the API, so the API only sees the proxy unless it trusts the forwarded header. `render.yaml` sets `ForwardedHeaders__TrustedNetworks__0=10.0.0.0/8`, Render's private range, so only the proxy (never the public internet) can supply `X-Forwarded-For`. Render does not document a fixed CIDR for its proxy, so verify this on the first deploy: log in repeatedly from two different networks (for example Wi-Fi and mobile data) and confirm that hitting the limit on one does not lock out the other. If both are locked out together, the proxy is outside that range: find its address in the request logs and replace the value with that CIDR. If you cannot get it right, remove the variable and accept that all users share one limit.

## 4. Frontend (Cloudflare Pages), second pass
1. In the Pages project, set the environment variable `VITE_API_BASE_URL` to the Render API URL (no trailing slash).
2. Redeploy. The value is baked in at build time, so changing it later also needs a redeploy.
3. Cloudflare may warn that `_redirects` (`/* /index.html 200`) is a loop; Pages still serves the SPA fallback correctly.

## Cold starts
Render's free service sleeps after ~15 minutes idle; the first request then takes 30-60 s. A keep-alive ping (e.g. UptimeRobot on `/health` every 10 minutes, free) avoids this, but 750 free hours cover one always-on service for a 31-day month (744 h) with almost no headroom, so do not add a second service. `/health` does not touch the database, so the pings keep Render awake but do not wake Neon; Neon pauses when idle and wakes in about a second on the first query.
